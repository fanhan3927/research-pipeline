# 分发链编排层

对应 `docs/PRD.md` 第 6.2 / 6.4 / 6.5 节。本文件是给执行编排任务的 Claude 看的操作手册，
不是给最终用户看的产品文档。

## 前置动作：建项目骨架

新项目开始时，先跑：

```
python scripts/init_project.py --name "<项目名称>" --chain distribution
```

得到 `projects/<项目名称>_<日期>/` 目录，本项目此后所有产出都落在这个目录下对应子目录，
不要散落在别处。同名项目已存在时（比如之前研发链先跑过）会在原目录上补齐子目录，不会
新建重复项目。

如果是接手一个已经跑了一部分的项目（比如换了个对话、或者隔了几天），先跑：

```
python scripts/project_status.py --project-dir <project_dir>
```

看一眼目录完成情况和暂停记录，确认从哪一步接着走，不要凭猜测重跑已经做过的步骤。

之后每完成一步自动动作，或者每次用户在人工确认/外部等待节点给出回应，
都要用 `scripts/audit_log.py append` 记一笔（见下方各步骤的日志要求）。

## 步骤 -1（人工确认）：适用性预检

**在触发 `hardtech-project-triage-matching` 之前先做这一步，不要省略。**

分发链的红线判定依据、红色事项覆盖面、A/B/C 定级门槛（营收规模、毛利率、量产阶段）、
13 类资金方画像、商务条款体系（财务顾问费/撮合服务费），整套设计都是围绕**硬科技老股
转让 / 成长期至 Pre-IPO 增资、且用户以中介撮合方身份介入**这一类特定交易构建的。这一点
是 Phase 4 用一个天使轮消费 AI 项目做压力测试时确认的：红线检查里 R8 整条依赖"转让方"
概念对增资类交易不适用，红色事项里 Y1/Y2/Y9/Y10 共 4 条是老股/锁定期专属、结构性不适用，
定级条件的营收/毛利率/量产阶段门槛会让任何早期项目机械落入 C 档（不是因为项目不好，
是因为这套门槛本来就没打算覆盖这个阶段），13 类资金方画像里没有一类明确覆盖天使轮阶段，
商务条款体系假设用户是收费中介而非直接投资人。

套一遍完整流程不会报错、也不会崩溃——大部分"不适用"和"不命中"字面结果一致，看起来像是
给出了完整结论，但那份结论对用户的决策没有实际信息量，等于白跑一趟五步。所以要在最前面
就先问，而不是跑完了才发现问不对题：

> 这个项目符合这几个特征吗？① 硬科技赛道（半导体/新能源/机器人/新材料/商业航天等，
> 不含纯消费互联网/消费级AI应用）② 老股转让，或已进入成长期至 Pre-IPO 阶段的增资
> ③ 你是以中介撮合方身份介入（要收财务顾问费/撮合服务费），不是以直接投资人身份评估要不要投

三条全部符合 → 继续走分发链正常流程（步骤 0 起）。
任意一条不符合 → 提示用户："这个项目和分发链的设计场景不完全对口，跑完整套流程能给出
字面结果，但信息量有限。更合适的选择可能是：赛道/阶段不对口 → 走研发链的
`pe-hardtech-screening`（Step 0 本身就覆盖天使轮到 Pre-IPO 全阶段的权重划分）；
身份是直接投资人而非中介 → 第 3 步的商务条件确认要跳过或改问'是否符合本机构的赛道/
阶段/规模策略'。要不要仍然跑一遍分发链（比如你就是想看看它会给出什么结论），还是切到
研发链？"由用户决定是否仍要继续。

日志：
```
python scripts/audit_log.py append <project_dir> --actor user \
  --step "分发链适用性预检" --detail "<三条是否符合的判断+用户决定>" --pause-type confirm
```

## 步骤 0（可选，外部等待）：材料太粗

如果用户给的材料只是几行文字，不够跑定级（对照 `hardtech-project-triage-matching` 的输入要求），
不要勉强定级。生成一份空白《硬科技项目信息采集表》（Word），提示用户"这份表发给项目方/转让方/FA后，
拿到回填版再回来"，然后停在这里。

日志：
```
python scripts/audit_log.py append <project_dir> --actor orchestrator \
  --step "生成空白采集表" --detail "材料不足以定级，等待项目方回填" --pause-type external_wait
```

用户带着回填后的采集表回来时，从步骤 1 继续，不用重新问已经问过的问题。

## 步骤 1-2：研判

触发 `hardtech-project-triage-matching`，把用户提供的材料喂给它。拿到红线检查、红色事项、
定级、排除清单、推送顺序后：

- **命中红线** → 告诉用户"命中红线，终止归档"，写日志，流程到此结束，不再往下走。
- **定级 C** → 告诉用户"定级 C，存档观察，不建议推送"，写日志，流程到此结束（用户仍可要求继续，
  但要明确提示"C 档通常不值得投入后续步骤"）。
- **定级 A / B** → 继续步骤 3，并按 6.4 节自动追加一句：
  "该项目定级为 {A/B}，是否要同时启动研发链做深度研判？"（这是两链衔接点，回答会记录下来，
  不阻塞分发链本身继续往下走）。

日志（自动步骤，无需暂停）：
```
python scripts/audit_log.py append <project_dir> --actor orchestrator \
  --step "研判" --detail "定级=<A/B/C>，命中红线=<有/无>，已排除客户=<...>"
```

## 步骤 3（人工确认）：商务条件

这一步不能替用户做，也不能瞎猜。明确停下来问：

> 确认一下商务条件：有没有财务顾问费？向谁收、多少个点？老股类的话折扣空间还有多少？
> 如果都没有，对方能给什么替代条件？

拿到回答后：
- **有收费空间** → 继续步骤 4
- **无费用无折扣** → 提示用户参考手册 7.3："放弃，或只做轻度撮合（转发信息，不做研判、
  不出材料、不安排尽调）"，问用户要放弃还是轻度撮合，并据此决定是否继续走完整流程。

日志：
```
python scripts/audit_log.py append <project_dir> --actor user \
  --step "商务条件确认" --detail "<用户的回答摘要>" --pause-type confirm
```

## 步骤 4：加工层

不是一个独立 skill，是编排层自己要执行的改写动作。参照原手册「三、加工」一节：

1. **剥离**：删除九类禁止上行信息（转让方真实转让原因、找了多久/被拒次数、实控人资金压力、
   谈判让步轨迹、私下让步空间、对项目方负面评价、内部 A/B/C 定级、已排除客户名单、全部商务条款）。
2. **改写**：项目亮点不能抄材料原文，必须重写，未经核实的表述要加"（项目方提供，未经独立核实）"。
3. **标注 + 如实保留**：折扣比例及计算基准、回购条款能否承继、是否估值倒挂、锁定期安排、
   已知重大风险——这些必须如实保留，不能因为"加工"就被一起删掉。判断标准：
   影响投资方对标的的估值判断 → 必须说；只影响用户自己的议价 → 不用说。

产出落在 `02_processing/`。这一步自动执行，不暂停，但输出要让用户能一眼看到"剥离了什么、
如实保留了什么"，方便他事后抽查。

## 步骤 5：入库

触发 `pipeline-intake`，把步骤 4 加工后的内容转成 14 字段（它自己的 STEP 2，产出一份
JSON）。**只用它做字段提取，不要用它自带的 Excel 生成脚本（STEP 4）产出最终 Pipeline
文件**——它自带脚本的表头命名（"所属赛道""入股估值""本次基金规模""拟上市交易所"……）
跟本项目 `make_external_pipeline.py` 期望的白名单表头（"赛道""入场估值""交易金额"
"目标上市地"……）不一致，直接拿它的输出往下传，对外版脚本会报"缺少白名单字段"。
拿到 JSON 后，自己用本项目的表头命名手动建/追加 Pipeline 内部版这一行（24 列，A-N
对外字段 + O-X 内部字段），落在 `03_pipeline/Pipeline_内部版.xlsx`。同时把 JSON 里
`confidence: missing` 的字段整理成一份信息缺口清单。

（这条踩坑是 Phase 4/6 真实材料验证时发现的：两个 skill 各自设计时用了不同的字段命名
习惯，独立看都没问题，接在一起才会报错。）

**5.1（外部等待，非阻塞）**：如果缺口清单不是空的，生成 Word 版发给用户去问项目方，
但不要因此卡住主流程——先按"缺失字段标 null"的版本继续走完剩余步骤，缺口回来了再更新对应字段。

日志：
```
python scripts/audit_log.py append <project_dir> --actor orchestrator \
  --step "入库" --detail "14 字段已提取，缺口=<N 项>"
python scripts/audit_log.py append <project_dir> --actor orchestrator \
  --step "生成信息缺口清单" --detail "等待项目方回复" --pause-type external_wait
```

## 步骤 6：内部列回填

把步骤 1（定级/红线/红色事项/排除清单/推送顺序）和步骤 3（商务条件状态）的结果，
填进 Pipeline 内部版的 O-X 十列（内部定级、命中红线、命中红色事项、已排除客户类型、
排除依据、推荐推送顺序、本方合作模式、商务条件状态、上次复核日期、内部备注）。
自动执行，不暂停。回填完成后，`03_pipeline/` 下应该有一份完整的 `Pipeline_内部版.xlsx`。

**这个文件本身永远不能进入外发路径**——不要在任何回答里建议用户直接发送这份文件。

## 步骤 7：生成对外版

跑脚本，不要手工删列：

```
python scripts/make_external_pipeline.py \
  --input <project_dir>/03_pipeline/Pipeline_内部版.xlsx \
  --output-dir <project_dir>/03_pipeline \
  --project-dir <project_dir>
```

脚本会自动：按白名单重建工作簿（14 列）、丢弃其他工作表、清空所有批注、清除隐藏列状态，
并做一遍关键词兜底扫描，同时把结果写进 audit_log.md。

## 步骤 8（人工确认）：发送前检查

脚本跑完会给出关键词扫描结果，但**不能替代人工确认**。把手册里的检查清单完整念给用户，
等他明确说"确认可以发"才算这一步完成：

> □ 只有 14 列　□ 只有一个工作表　□ 没有批注　□ 全选取消隐藏后没有隐藏列
> □ 关键词扫描结果已看过　□ 文件名是"对外版"不是"内部版"

日志（脚本已经自动写了 pending 的一条，用户确认后追加一条 actor=user 的记录）：
```
python scripts/audit_log.py append <project_dir> --actor user \
  --step "发送前检查确认" --detail "用户确认可以发送" --pause-type confirm
```

到这里，分发链完成。`03_pipeline/Pipeline_对外版_<日期>.xlsx` 是唯一允许外发的文件。

## 两链衔接（PRD 6.4）

- 步骤 2 定级 A/B 时问过"是否启动研发链"，如果用户当时或事后同意，切到
  `orchestrator/rd-chain`，用 `python scripts/init_project.py --name "<同一个项目名>" --chain rd`
  在同一个项目目录上补齐研发链需要的子目录，并把已有材料、triage 结论中可复用的字段传过去，
  不要求用户重新上传一遍。
- 研发链算出退出估值后，会由研发链那边跑 `scripts/backfill_exit_valuation.py` 回填进本项目
  `03_pipeline/Pipeline_内部版.xlsx` 的"退出估值"列，并自动重新生成对外版（该字段可以进
  Pipeline，无论内部版还是对外版）。分发链这边不需要手动做这一步，但要知道：一旦研发链
  跑了这个脚本，`03_pipeline/` 下会多一份新日期的对外版文件，**这份新文件也要走一遍发送前
  检查，不能因为"之前检查过一次"就直接发**。
- **入场价格上限任何情况下都不允许写入 Pipeline 的任何版本**。这不只是一条要遵守的规则——
  本项目故意没有提供任何"往 Pipeline 写任意字段"的通用脚本，唯一能写 Pipeline 的脚本
  （`backfill_exit_valuation.py`）参数里就只有"退出估值"这一个值可写，写不了别的字段。
  如果用户坚持要把入场价格上限之类的内部信息记进 Pipeline 内部版，只能手工编辑 Excel，
  这本身就是一个刻意、显眼的动作，不会被日常流程悄悄带过；遇到这种要求要先提醒风险
  （哪怕手工加进了内部版，也绝不能出现在对外版脚本的白名单列里，且 `make_external_pipeline.py`
  会在检测到类似字段名时打印结构性提醒，见该脚本的 `ENTRY_PRICE_CAP_HEADER_HINTS`）。
